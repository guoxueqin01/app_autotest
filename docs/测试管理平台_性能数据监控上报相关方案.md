# 测试管理平台 — 性能数据监控与上报方案

> 本文是 AtomX 自动化框架的**姊妹文档**，聚焦在测试管理平台侧的完整设计：**存储 + 分析 + 展示**。
>
> 自动化框架侧只负责「执行 + 采集 + 上报」（见 `docs/app自动化方案_最终版.md` §18），平台侧接住 `Reporter` 上报的数据契约，负责：
> - 存储：多引擎分层的持久化
> - 分析：跨版本、跨设备、跨执行的聚合与基线
> - 展示：报告中心 / 失败复现 / 性能大盘 / 设备基线 / 趋势看板
>
> 本文不对框架侧做任何变更；两端通过统一的 `Reporter` 数据契约解耦。

---

## 一、整体架构

### 1.1 端到端链路

```
┌──────────────────┐   HTTP/JSON    ┌──────────────────┐   后台处理    ┌──────────────────┐
│  AtomX 自动化框架 │ ─────────────▶ │  测试管理平台 API  │ ───────────▶ │  持久化存储层     │
│  (执行+采集+上报) │                │  (接收/校验/路由)  │              │  MySQL+OSS+InfluxDB+ES│
└──────────────────┘                └──────────────────┘              └──────────────────┘
                                                              │
                                                              ▼
                                                    ┌──────────────────┐
                                                    │  分析与聚合引擎    │
                                                    │  (定时任务/Kafka) │
                                                    └──────────────────┘
                                                              │
                                                              ▼
                                                    ┌──────────────────┐
                                                    │  前端展示层        │
                                                    │  (报告/复现/大盘) │
                                                    └──────────────────┘
```

### 1.2 分层职责

| 层 | 组件 | 职责 |
|---|---|---|
| **上报接入层** | `report-api` | 接收 AtomX `Reporter` HTTP 上报，鉴权、限流、幂等 |
| **持久化层** | MySQL / OSS / InfluxDB / ES | 关系数据 / 大文件 / 时序数据 / 全文检索 |
| **分析层** | 定时任务 / Flink / Kafka Streams | 跨版本聚合、基线计算、异常检测、每日快照 |
| **查询层** | Query API | 面向前端的聚合查询接口 |
| **展示层** | Web 前端 | 报告中心、失败复现、性能大盘、设备基线 |

## 二、存储引擎选型

### 2.1 分而治之

不同数据特性走不同存储引擎，避免单一大库承担所有场景：

| 数据 | 特性 | 存储引擎 | 保留期 |
|---|---|---|---|
| 用例结果（case_result / run / tag） | 强一致、多查询维度 | **MySQL 8 / PostgreSQL 14** | 1 年 |
| 操作轨迹（action） | 高写入、按 case_id 检索 | **MySQL JSON 字段 或 ClickHouse** | 3 个月 |
| 二进制证据（截图 / 录屏 / UI 树） | 大文件、CDN 分发 | **OSS / S3 / MinIO** | 截图 6 个月 / 录屏 1 个月 |
| 性能时序（CPU / 内存 / FPS / 电量） | 高写入、时序查询 | **InfluxDB 2 / TDengine / Prometheus TSDB** | 90 天明细 + 1 年聚合 |
| 全文检索（错误栈 / 日志 / UI 树） | 关键词、模糊搜索 | **Elasticsearch 8 / OpenSearch** | 6 个月 |
| 汇总指标（通过率 / 平均耗时） | 读多写少、看板展示 | MySQL 物化表 或 **ClickHouse** | 3 年 |

### 2.2 为什么不全部塞进一个数据库

- 录屏和截图文件太大，MySQL 存 blob 会撑爆磁盘 → **OSS**
- CPU / 内存每秒级采样，MySQL 写入扛不住 → **InfluxDB**
- 错误栈和日志需要跨执行关键词搜索 → **ES**
- 汇总数据量大、聚合查询 → **ClickHouse 或 MySQL 物化表**

## 三、数据模型

### 3.1 核心领域模型

```
Project (项目)
  └─ Run (一次 CI 执行 / 一次 pytest run)
      ├─ CaseResult (单条用例的执行结果)
      │   ├─ ActionRecord* (操作轨迹)
      │   ├─ Evidence* (失败证据)
      │   └─ PerfSnapshot* (性能采样)
      ├─ DeviceSnapshot (本次涉及的设备)
      └─ Tag (标签: module / priority / epic / story)
```

### 3.2 MySQL 表结构

#### 3.2.1 基础元数据表

```sql
-- 项目表：一个 App / 一个业务线 = 一个 project
CREATE TABLE project (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    name          VARCHAR(128) NOT NULL UNIQUE,      -- 项目名 (e.g. "AtomX-Ecommerce")
    code          VARCHAR(32) NOT NULL UNIQUE,        -- 短码 (e.g. "ATOMX-EC")
    owner         VARCHAR(64),                         -- 负责人
    product       VARCHAR(128),                        -- 产品线
    description   VARCHAR(512),
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_code (code)
) ENGINE=InnoDB COMMENT='项目';

-- 应用版本表：一次 build / 一次发布 = 一个 app_version
CREATE TABLE app_version (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    project_id    BIGINT NOT NULL,
    version       VARCHAR(32) NOT NULL,                -- e.g. "1.2.3"
    build_number  INT,                                 -- CI build number
    channel       VARCHAR(32),                         -- release / beta / internal
    platform      VARCHAR(16) NOT NULL,                -- android / ios / harmony
    install_size_mb INT,
    min_sdk       VARCHAR(32),                         -- e.g. "android-24", "ios-14"
    release_date  DATE,
    notes         TEXT,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_version (project_id, platform, version),
    INDEX idx_project_platform (project_id, platform),
    FOREIGN KEY (project_id) REFERENCES project(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='App 版本';

-- 设备表：平台维护的设备基线库
CREATE TABLE device (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    project_id    BIGINT NOT NULL,
    serial        VARCHAR(64) NOT NULL,                -- adb serial / udid
    brand         VARCHAR(32),                         -- samsung / huawei / apple
    model         VARCHAR(64),                         -- SM-G9910 / iPhone 13
    platform      VARCHAR(16) NOT NULL,
    os_version    VARCHAR(32),                         -- 13.0 / 14.2.1
    cpu_arch      VARCHAR(16),                         -- arm64 / arm64e / armv7l
    screen_w      INT,
    screen_h      INT,
    memory_mb     INT,
    storage_mb    INT,
    role          VARCHAR(16) DEFAULT 'pool',          -- pool / baseline / reserved
    tags          JSON,                                -- ["flagship", "low-end"]
    status        VARCHAR(16) DEFAULT 'active',        -- active / retired
    first_seen_at DATETIME,
    last_seen_at  DATETIME,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_serial (serial),
    INDEX idx_project_platform (project_id, platform),
    INDEX idx_brand_model (brand, model),
    FOREIGN KEY (project_id) REFERENCES project(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='设备基线库';
```

#### 3.2.2 用例执行相关表（核心）

```sql
-- Run 表：一次 pytest 执行 / 一次 CI 构建
CREATE TABLE test_run (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    project_id      BIGINT NOT NULL,
    app_version_id  BIGINT,                             -- 关联被测版本
    run_id          VARCHAR(64) NOT NULL UNIQUE,        -- 框架生成的 run_id
    trigger_source  VARCHAR(32) NOT NULL,               -- ci / manual / scheduled
    ci_run_url      VARCHAR(512),                       -- GitHub Actions / Jenkins URL
    branch          VARCHAR(64),                        -- main / release-1.2
    commit_sha      VARCHAR(40),
    commit_message  VARCHAR(512),
    triggered_by    VARCHAR(64),                        -- 触发人 / 机器人
    started_at      DATETIME(3) NOT NULL,
    finished_at     DATETIME(3),
    duration_ms     INT GENERATED ALWAYS AS (
                        TIMESTAMPDIFF(MICROSECOND, started_at, finished_at) DIV 1000
                    ) STORED,
    total_count     INT DEFAULT 0,
    passed_count    INT DEFAULT 0,
    failed_count    INT DEFAULT 0,
    skipped_count   INT DEFAULT 0,
    error_count     INT DEFAULT 0,
    duration_avg_ms INT,                                -- 本次 run 用例平均耗时
    duration_p95_ms INT,
    pass_rate_pct   DECIMAL(5,2) DEFAULT 0,             -- 通过率 %
    status          VARCHAR(16) DEFAULT 'running',      -- running / success / failed / aborted
    metadata_json   JSON,                               -- 其他扩展信息
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_project_time (project_id, started_at DESC),
    INDEX idx_ci_url (ci_run_url),
    INDEX idx_branch_commit (branch, commit_sha),
    FOREIGN KEY (project_id) REFERENCES project(id) ON DELETE CASCADE,
    FOREIGN KEY (app_version_id) REFERENCES app_version(id) ON DELETE SET NULL
) ENGINE=InnoDB COMMENT='测试执行';

-- CaseResult 表：单条用例结果 (每个 Run 可能产生几千到几万行)
CREATE TABLE case_result (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    run_id          BIGINT NOT NULL,
    case_id         VARCHAR(256) NOT NULL,              -- testcases/login/test_login.py::test_admin
    title           VARCHAR(256),                       -- 展示标题
    module          VARCHAR(64),                        -- login / order / profile
    priority        VARCHAR(16),                        -- p0 / p1 / p2 / p3
    severity        VARCHAR(16),                        -- blocker / critical / major / minor
    result          VARCHAR(16) NOT NULL,               -- passed / failed / skipped / error
    duration_ms     INT NOT NULL DEFAULT 0,
    retry_count     INT DEFAULT 0,                      -- 重跑次数
    error_type      VARCHAR(64),                        -- AssertionError / Timeout / Crash
    error_message   TEXT,                               -- 简短错误摘要
    error_stack     MEDIUMTEXT,                         -- 完整堆栈
    screenshot_url  VARCHAR(512),                       -- OSS URL (失败时)
    video_url       VARCHAR(512),                       -- OSS URL (失败录屏)
    ui_tree_url     VARCHAR(512),                       -- OSS URL
    actions_count   INT DEFAULT 0,                      -- 操作轨迹条数
    started_at      DATETIME(3) NOT NULL,
    finished_at     DATETIME(3),
    platform        VARCHAR(16) NOT NULL,
    device_id       BIGINT,
    app_version_id  BIGINT,
    tags            JSON,                               -- ["smoke", "regression", "android"]
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_run_case (run_id, case_id),           -- 一次 run 一条用例只能上报一次
    INDEX idx_run_result (run_id, result),
    INDEX idx_case_result (case_id, result),
    INDEX idx_result_time (result, started_at DESC),
    INDEX idx_module_priority (module, priority),
    FOREIGN KEY (run_id) REFERENCES test_run(id) ON DELETE CASCADE,
    FOREIGN KEY (device_id) REFERENCES device(id) ON DELETE SET NULL,
    FOREIGN KEY (app_version_id) REFERENCES app_version(id) ON DELETE SET NULL
) ENGINE=InnoDB COMMENT='用例执行结果';

-- 标签关联表（多对多）
CREATE TABLE tag (
    id    BIGINT PRIMARY KEY AUTO_INCREMENT,
    name  VARCHAR(64) NOT NULL UNIQUE,                  -- 标签名
    type  VARCHAR(16) DEFAULT 'general',                -- general / module / priority / epic
    color VARCHAR(16)
) ENGINE=InnoDB COMMENT='标签';

CREATE TABLE case_result_tag (
    case_result_id BIGINT NOT NULL,
    tag_id         BIGINT NOT NULL,
    PRIMARY KEY (case_result_id, tag_id),
    INDEX idx_tag (tag_id),
    FOREIGN KEY (case_result_id) REFERENCES case_result(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id) REFERENCES tag(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='用例-标签关联';
```

#### 3.2.3 操作轨迹与证据表

```sql
-- 操作轨迹表：每次 tap / swipe / input / assert 一行
-- 高写入场景，可后续拆到 ClickHouse
CREATE TABLE action_record (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    case_result_id BIGINT NOT NULL,
    seq           INT NOT NULL,                         -- 序号 (1, 2, 3 ...)
    ts            DATETIME(3) NOT NULL,                 -- unix 时间戳
    action        VARCHAR(32) NOT NULL,                 -- tap / swipe / input / assert / wait
    locator       JSON,                                 -- 定位器 JSON
    args_json     JSON,                                 -- 参数
    duration_ms   INT DEFAULT 0,
    result        VARCHAR(16) DEFAULT 'ok',             -- ok / fail / timeout
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_case_seq (case_result_id, seq),
    INDEX idx_case_time (case_result_id, ts),
    INDEX idx_action (action),
    FOREIGN KEY (case_result_id) REFERENCES case_result(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='操作轨迹';

-- 证据元数据表：二进制文件本体存 OSS，这里只存索引
CREATE TABLE evidence (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    case_result_id  BIGINT NOT NULL,
    kind            VARCHAR(16) NOT NULL,                -- screenshot / video / ui_tree / stack / log
    mime            VARCHAR(64) NOT NULL,                -- image/png / video/mp4 / text/xml
    name            VARCHAR(256),                        -- 建议文件名
    storage_type    VARCHAR(16) DEFAULT 'oss',           -- oss / inline
    storage_key     VARCHAR(512),                        -- OSS object key (e.g. /proj/run/xxx/xxx.png)
    content_inline  MEDIUMBLOB,                          -- 小文件 (<1MB) 直接内联存 DB
    size_bytes      INT DEFAULT 0,
    checksum_sha256 CHAR(64),
    duration_seconds DECIMAL(8,2),                       -- 视频时长
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_case_kind (case_result_id, kind),
    INDEX idx_storage_key (storage_key),
    FOREIGN KEY (case_result_id) REFERENCES case_result(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='失败证据索引';
```

#### 3.2.4 性能数据表（时序聚合）

```sql
-- 性能快照表：一次用例执行的性能聚合结果 (非原始时序)
-- 原始时序数据存 InfluxDB，这里存聚合后的摘要
CREATE TABLE perf_snapshot (
    id                BIGINT PRIMARY KEY AUTO_INCREMENT,
    case_result_id    BIGINT NOT NULL,
    metric            VARCHAR(32) NOT NULL,              -- cpu_percent / memory_mb / fps / battery / net_rx / net_tx
    start_ts          DATETIME(3) NOT NULL,
    end_ts            DATETIME(3) NOT NULL,
    sample_count      INT NOT NULL,                      -- 采样点数
    min_value         DECIMAL(12,4) NOT NULL,
    max_value         DECIMAL(12,4) NOT NULL,
    avg_value         DECIMAL(12,4) NOT NULL,
    p95_value         DECIMAL(12,4),
    p99_value         DECIMAL(12,4),
    last_value        DECIMAL(12,4),
    stddev_value      DECIMAL(12,4),
    is_anomaly        TINYINT(1) DEFAULT 0,              -- 是否异常
    anomaly_reason    VARCHAR(256),                      -- e.g. "cpu > baseline_p95"
    created_at        DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_case_metric (case_result_id, metric),
    INDEX idx_metric_time (metric, start_ts DESC),
    INDEX idx_anomaly (is_anomaly, metric),
    FOREIGN KEY (case_result_id) REFERENCES case_result(id) ON DELETE CASCADE
) ENGINE=InnoDB COMMENT='性能快照 (聚合)';

-- 性能时序查询代理表：不存明细，只存指向 InfluxDB 的 measurement
-- 明细走 InfluxDB 的 CSV 导出，MySQL 只存聚合
-- (可选：如需高可用可存 ClickHouse 分区表)
```

### 3.3 对象存储（OSS）目录规范

```
oss://atomx-tmc-prod/
├── project-{code}/
│   └── run-{run_id}/
│       ├── meta.json                                  # 冗余存一份 run 元数据方便离线分析
│       ├── case-{case_result_id}/
│       │   ├── screenshot_{ts}.png                    # 失败截图
│       │   ├── video_failure_{ts}.mp4                 # 失败录屏
│       │   ├── ui_tree_{ts}.xml                       # UI 树 XML
│       │   ├── stack_{ts}.txt                         # 错误堆栈文本
│       │   ├── logcat_{ts}.log                        # 设备日志
│       │   └── evidence_index.json                    # 该 case 的所有 evidence 元数据
│       └── actions/
│           └── case-{case_result_id}.jsonl            # 操作轨迹全量（可选，默认只写 DB）
└── baseline/                                          # 基线样本导出，供离线复算
    └── project-{code}/
        └── baseline_{metric}_{platform}_{date}.parquet
```

**命名规范**：
- 所有对象 key 都包含 `project_code / run_id / case_result_id`，方便分片与清理
- 时间戳用 ISO 8601，避免本地化
- 二进制文件超过 1MB 走 OSS，小于 1MB 直接内联到 MySQL `content_inline`

**权限与生命周期**：
- CDN 只暴露只读 URL，写入走独立账号
- OSS 生命周期规则：截图 6 个月后删除，录屏 1 个月后删除，UI 树 90 天后删除
- 关键失败证据可设置 `pin=true` 长期保留

### 3.4 时序数据库（InfluxDB 2 / TDengine）Schema

```
Measurement:  perf_metrics
Tag keys:     project_code, run_id, case_result_id, platform, device_serial, device_model
Field keys:   cpu_percent, memory_pss_kb, memory_mb, fps, battery_level, net_rx_bytes, net_tx_bytes

Retention:
  - detail  90 days  (原始采样)
  - hourly  1 year   (每小时聚合)
  - daily   3 years  (每日聚合)

Example point:
  perf_metrics,project=ATOMX-EC,run=abc,case=123,platform=android,serial=EMUX123,device=SM-G9910 \
    cpu_percent=23.5,memory_pss_kb=184320 \
    1712979200000000000
```

## 四、上报 API 设计

### 4.1 端点

```
POST   /api/v1/report/run/start         # Run 开始 (可选，框架不报的话平台自己建)
POST   /api/v1/report/case              # 上报单条用例结果 (含 actions + evidence + perf)
POST   /api/v1/report/perf/batch        # 批量上报性能时序 (独立通道)
POST   /api/v1/report/run/finish        # Run 结束
POST   /api/v1/report/evidence/upload   # 大文件分片上传 (OSS 预签名)
```

### 4.2 鉴权

- Bearer Token：`Authorization: Bearer <token>`
- Token 按 project 绑定，一个 project 一个 token
- 支持短期 token + 定期轮换
- 每个 token 限制 QPS（默认 100 QPS / project）

### 4.3 幂等

- 请求头带 `Idempotency-Key: <case_id + run_id>`
- 服务端 24 小时内相同 key 请求返回同一结果
- 支持客户端重试不产生重复数据

### 4.6 限流与降级

- 单 project 默认 100 QPS 上报限制
- 触发限流返回 `429 Too Many Requests` + `Retry-After: 5`
- 框架侧应做指数退避重试（见框架侧 §18.4 `PlatformReporter`）
- 服务端异常时，框架侧应把数据写入本地磁盘队列，下次执行前合并上报

## 五、后台任务与聚合分析

### 5.1 任务清单

| 任务 | 触发 | 输入 | 输出 |
|---|---|---|---|
| `case_aggregator` | Run 结束时 | `case_result` 表 | 更新 `test_run.passed_count` 等 |
| `daily_snapshot` | 每日 03:00 | 昨日 case_result | 写入 `daily_snapshot` |
| `perf_baseline_recompute` | 每周日 04:00 | 最近 90 天 perf_snapshot | 更新 `perf_baseline` |
| `anomaly_detect` | 每次 case_result 上报后 | perf_snapshot + 基线 | 标记 `is_anomaly`，触发告警 |
| `flaky_case_detect` | 每日 | 最近 30 天 case_result | 标记 flaky 用例，写入 `daily_snapshot.flaky_cases` |
| `oss_lifecycle_cleanup` | 每日 05:00 | OSS 生命周期 | 按规则清理老证据 |
| `report_share_gen` | Run 结束后 5 分钟 | 当次 run 数据 | 生成 HTML 邮件 / IM 消息 |
| `device_baseline_sync` | 每日 02:00 | device 表 + 最近使用记录 | 更新 `last_seen_at`，标记 retired |

### 5.2 基线算法

**性能基线（`perf_baseline`）**：

```
给定 (case_id, metric, platform, device_model) 维度：
1. 从 perf_snapshot 取最近 90 天成功用例的样本
2. 剔除异常值：使用 IQR 剔除 [Q1 - 1.5*IQR, Q3 + 1.5*IQR] 之外的点
3. 计算 p50 / p90 / p95 / p99 / mean / stddev
4. 阈值：
   - warn: baseline_p95 * 1.1
   - fail: baseline_p99 * 1.2
```

**通过率基线**：
- 每日计算每个 `module + priority` 维度的通过率
- 与近 30 天均值对比，超过 5 个百分点视为异常
- 触发告警并推送到 IM 群

### 5.3 Flaky 用例检测

```
输入：最近 30 天同一 case_id 的所有执行结果
算法：
  - 若执行次数 >= 5 且通过率 ∈ (50%, 90%]: flaky
  - 若执行次数 >= 3 且通过率 == 100% 但历史曾失败: recover_flaky
  - 若连续 3 次以上失败: unstable (更严重)
输出：写入 daily_snapshot.flaky_cases 字段
```

### 5.4 异常检测

**单次异常**（写入 `perf_snapshot.is_anomaly`）：
- 单次采样的 max 超过 baseline_p99 * 1.2 → 严重异常
- 单次采样的 max 超过 baseline_p95 * 1.1 → 预警
- 内存泄漏检测：单调递增且斜率 > baseline_std * 0.5

**跨执行异常**：
- 同一 case_id 的 duration_ms 相对基线 > 1.5x → 性能回归
- 同一 error_type 在 24 小时内出现 >= 5 次 → 疑似 Bug 群

## 八、与框架对接的完整协议

### 8.1 时序图

```
AtomX 用例        PlatformReporter      测试管理平台 API      MySQL/OSS/InfluxDB
    │                    │                    │                    │
    │── test_xxx() ─────▶│                    │                    │
    │                    │                    │                    │

    │                    │── POST /report/case─▶│                    │
    │                    │   (JSON body)      │                    │

    │                    │                    │── INSERT action_record─▶
    │                    │                    │                    │
    │                    │                    │── PUT OSS ──────────▶
    │                    │                    │  (evidence)         │
    │                    │                    │                    │
    │                    │                    │── INSERT perf_metrics─▶
    │                    │                    │  (InfluxDB)        │
    │                    │                    │                    │
    │                    │◀── 200 OK ─────────│                    │
    │                    │◀──────────── {case_result_id: xxx}      │
    │◀─ 用例结束 ───────│                    │                    │
```

### 8.2 数据流向

1. **框架侧**：`AtomX` 执行用例，`ReporterPlugin` 收集 actions / evidence / performance 到内存
2. **上报**：用例结束时 `Reporter.report_case()` 序列化 `CaseReport` 为 JSON，POST 到平台 API
3. **接收**：`report-api` 校验、鉴权、幂等检查
4. **路由**：按数据类型分发
   - `case_result` / `action_record` / `evidence` → MySQL
   - `evidence[].data_base64`（>1MB） → OSS
   - `performance.*` → InfluxDB
   - `error_stack` / `log` → Elasticsearch
5. **异步处理**：`analysis-worker` 消费消息队列，跑聚合任务
6. **展示**：`query-api` 聚合查询，前端渲染

## 九、生命周期管理

### 9.1 数据保留策略

| 数据 | 明细保留 | 聚合保留 | 归档 |
|---|---|---|---|
| case_result | 12 个月 | 3 年 (daily_snapshot) | 转冷存储 |
| action_record | 3 个月 | - | 删除 |
| evidence (screenshot) | 6 个月 | - | 删除 |
| evidence (video) | 1 个月 | - | 删除 |
| evidence (ui_tree) | 90 天 | - | 删除 |
| perf 时序 (InfluxDB detail) | 90 天 | 1 年 (hourly) + 3 年 (daily) | - |
| 错误堆栈 (ES) | 6 个月 | - | 删除 |
| 项目配置 / 设备基线 / 用户 | 长期 | - | 不删除 |

### 9.2 冷热分离

- **热数据**：最近 90 天 case_result + 每日快照，走主库主从
- **温数据**：90 天 - 1 年，走 MySQL Archive 表 / ClickHouse
- **冷数据**：> 1 年，导出 Parquet 存 OSS，需要时按需查询

### 9.3 版本管理

- App 版本表 (`app_version`) 保留所有历史版本
- 每次 run 关联一个 `app_version_id`
- 版本废弃后不删除记录，标记为 `retired`，历史查询不受影响

### 10.1 性能指标

| 指标 | 目标 |
|---|---|

- 二进制证据 99.99% 完整（3 副本 OSS）
- 数据库主从同步，RPO < 5min, RTO < 30min
- 上报失败自动重试，客户端本地队列保底

### 10.3 安全

- 所有 API 强制 HTTPS
- Token 90 天轮换
- 二进制证据 URL 使用预签名，1 小时过期
- 敏感字段（如用户账号）上报前脱敏
- 审计日志：所有操作记录到 audit_log 表

### 10.4 扩展性

- 支持水平扩展 `report-api` / `query-api` 实例
- MySQL 分表策略：`case_result` 按 `run_id` 分片，每月一个分片
- InfluxDB 集群分片按 project 分区
- OSS 天然分布式

## 十二、常见问题

**Q1：为什么不直接把所有数据存到 MySQL 一个大库？**
答：视频录屏动辄几十 MB，MySQL 存 blob 会撑爆磁盘、拖慢查询。二进制走 OSS、时序走 InfluxDB 是标准做法。

**Q2：为什么需要 ES 单独存错误栈？**
答：错误栈是高频搜索场景（"最近一周 NullPointerException"），MySQL LIKE 查询在千万级数据下会 timeout。ES 全文检索能毫秒级返回。

**Q3：为什么 case_result 要按 run_id 分表？**
答：单表行数会快速增长（每天几千个 run × 几千个 case = 千万级），按月分表可以让历史查询不阻塞新数据写入。

**Q4：性能时序为什么要 InfluxDB？**
答：性能采样是每秒多次的写入，MySQL 主键写入会成为瓶颈。InfluxDB 的 append-only 存储模型 + 压缩率，是这类数据的标准答案。

**Q5：告警如何避免风暴？**
答：告警规则带冷却窗口（默认 30 分钟），同一规则的重复触发合并；跨项目合并（多项目同时告警只发一次汇总）。

**Q6：框架侧上报失败了怎么办？**
答：`PlatformReporter` 内置指数退避重试 3 次，仍失败写入本地磁盘队列；下次框架启动时先合并上报积压数据，避免数据丢失。

**Q7：跨项目共享基线吗？**
答：默认不共享。基线是 project_id + case_id + platform 的复合维度，不同项目数据不混。跨项目对比在 P3 阶段通过 dashboard 查询实现，不写入 baseline 表。

## 十三、总结

测试管理平台的核心是**分层存储 + 异步分析 + 分层展示**：

- **存储层**：MySQL 存关系数据、OSS 存二进制、InfluxDB 存时序、ES 存搜索
- **分析层**：定时任务做聚合、基线、异常检测、flaky 识别
- **展示层**：报告中心、用例详情、性能大盘、设备基线、趋势看板、告警中心

框架只负责"生成数据并推送到 API"，平台负责"存下来、算出来、展示出来"。两端通过 `Reporter` 数据契约解耦，任何一方迭代都不影响另一方。
